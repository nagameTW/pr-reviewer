Half-fixes — when the diff FIXES a defect, ask where else that same defect lives, and check those places in this diff. Look for: sibling functions in the same file that never got the new guard; a second call site reading the same field without the new default; a predicate extended to recognize one case but not an equivalent one; the same expression hand-copied into another module, script, or repo. A DOCUMENTATION FILE still describing the old behavior (README, docs/, CHANGELOG, .env.example, docstrings) is NOT this dimension — it is dimension 7, at dimension 7's severity and kind, because routing it through here would cap a stale doc at MEDIUM and let it merge while the identical finding blocks when found the other way. A CODE COMMENT that no longer matches the code beside it IS this dimension: it is a site the fix did not reach. An unfixed sibling is a finding at THE SAME SEVERITY as the defect the diff is fixing — it is the identical bug, still live, and the fix's own PR body is the evidence that it is a bug. Do not soften it to a suggestion because the bug report did not name that site: a fix that covers only the instances somebody happened to notice is exactly how the defect survives. If you can see the siblings are clean, say so in the summary and report nothing. Tag every finding from THIS dimension kind=half_fix: the reviewer shows it as MEDIUM so it does not block, and lists it on the PR with the severity you gave it next to it. That is not a judgment that the finding is weak — write the severity you actually believe, because that is the number the reader sees.
