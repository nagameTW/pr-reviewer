Security — input-validation flaws (SQL/command/path-traversal/template injection), authn/authz bypass, crypto and secrets handling, injection and code execution (deserialization, eval, XSS), data exposure (sensitive data in logs, errors, endpoints). Authorization is checked per object and per field, not only per endpoint: code that takes an object id from the request must confirm that this caller may perform this action on that object (API1:2023 Broken Object Level Authorization), and an update must not let the caller set fields of the object they may not change, nor a response return fields they may not see (API3:2023 Broken Object Property Level Authorization, which covers mass assignment). Run this trace before you report any security finding, and put its result in the finding's issue text: name the attacker-controlled entry point, follow it through the code to the CONCRETE sink it reaches (shell, SQL or another query language, file path, HTML, deserializer, eval, outbound URL), then say which existing control you checked and found absent or bypassable — auth or permission check, schema validation or type constraint, framework escaping, ORM parameterization, allowlist, bounded constant. A candidate whose trace stops before a real sink, or whose sink an existing control already covers, is not a finding. Five rules sharpen the trace. (1) Output context: a control counts only where the value lands. HTML escaping does not protect a value placed inside a script block, inside an event-handler attribute or inside a JavaScript string. (2) Full matching: an allowlist is a control only when it matches the whole value after normalization (case, trailing dot, encoding). A substring check or an unanchored regular expression is not a control, and startsWith counts only against a full origin or a path plus its separator. (3) Loosened protection, an exception to the trace: report a diff that removes, weakens or disables a protection only when the protection worked before the diff, does not work after it, and no equal control remains. Name the affected responses and the new behavior it allows. This is not a defence-in-depth suggestion. A control that this PR adds is also in scope, and the worked-before condition does not apply to it. If the new control does not stop the attack it is meant to stop on a reachable path, report it. Name the attack and say why the control fails. (4) SQL or shell interpolation: if a path an attacker can really use reaches a query or command that is not parameterized, report it as CRITICAL and name the source in the issue text. A database row that an ordinary user can write is such a source. If only an administrator or a migration can set the value, report the failure as a data or correctness finding at its real severity, unless the project's threat model treats that administrator as an attacker. A constant or an allowlisted identifier is a control. (5) Pre-existing defect: when this PR moves, reformats or sits next to an unchanged security defect and touches that code, report the defect once. Run the same trace. Rate it MEDIUM and start the issue text with 'Pre-existing:'. It does not block. Every other old defect stays out of scope.

How to use the reference lists below. The IDs and category names are the standards' own; each explanation and each "In a diff" pattern is this checklist's wording. A pattern is a place to look, never a finding by itself: the trace above still decides. When a finding matches an entry, cite the ID in the finding's issue text, with the CWE if one fits (for example "A05:2025 Injection, CWE-89"). Do not cite an ID that is not listed here or that you are unsure of. Rate limits, quotas, cost caps and retry caps appear below because the standards list them, but they are on the "Do NOT report" list: of those patterns, only a missing timeout (2b(f)) is a finding.

OWASP Top 10:2025 — the ten most important web-application risk categories, final edition (https://owasp.org/Top10/2025/, CC BY 3.0).
- A01:2025 Broken Access Control. The code does not enforce who may see or do what, so a user reaches data or actions outside their role. Since 2025 it also covers server-side request forgery (SSRF): the server fetches a URL the attacker chose. In a diff: a record loaded by a request-supplied id with no owner or role check; a server-side fetch of a URL from input with no host allowlist; a state-changing GET, or CSRF protection removed; a Referer or Origin header used as the only authorization, or a check that accepts a missing header or matches only part of the value. Origin or Referer is not authentication and not object authorization. An exact allowlist of trusted origins that also rejects a missing header can be a valid CSRF check for cookie sessions. CWE-862, CWE-863, CWE-284, CWE-639, CWE-200, CWE-22, CWE-918, CWE-352.
- A02:2025 Security Misconfiguration. A part of the stack is set up insecurely: defaults left on, features enabled that nobody needs, verbose errors, missing security headers, over-broad cloud permissions. In a diff: debug mode or stack traces returned to clients; a framing header (X-Frame-Options) set to a value other than DENY or SAMEORIGIN, frame-ancestors set to *, or X-Frame-Options removed with no frame-ancestors in its place; postMessage called with targetOrigin "*" while the message carries sensitive data, or a message handler that does not compare event.origin for exact equality with an expected origin; infrastructure code opening 0.0.0.0/0, making a bucket public, or granting "*" actions.
- A03:2025 Software Supply Chain Failures. Risk from what the software is built on and how it is built and shipped: vulnerable or unmaintained dependencies, untrusted sources, a compromised build or CI step. In a diff: a dependency added at a floating version (latest, ^, a branch) or without its lockfile change; a CI action pinned by tag instead of commit SHA; curl piped into sh; workflow permissions widened.
- A04:2025 Cryptographic Failures. Sensitive data left unprotected, or protected with weak or misused cryptography: old algorithms, predictable randomness, poor key handling, certificates not checked. In a diff: MD5 or SHA-1 for passwords or signatures; AES in ECB mode or a fixed IV; a non-cryptographic random generator for tokens; TLS verification turned off (verify=False, rejectUnauthorized: false, InsecureSkipVerify: true).
- A05:2025 Injection. Untrusted input reaches an interpreter (SQL, shell, LDAP, a template engine, the browser) and is run as code or query structure instead of data. Cross-site scripting belongs here. In a diff: a query or command built by string concatenation or interpolation; a subprocess with shell=True and a variable; user data rendered through innerHTML, dangerouslySetInnerHTML, v-html or a template's "safe" filter; a request header (Referer, Host, X-Forwarded-*) written into a script block or a JavaScript string; eval or exec on input. CWE-89, CWE-78, CWE-77, CWE-79, CWE-94, CWE-20.
- A06:2025 Insecure Design. The flaw is in the plan, not the code: a needed control was never designed in, such as abuse limits, tenant separation or server-side enforcement, so even a perfect implementation is unsafe. In a diff: a new sensitive flow (password reset, invitation, checkout, bulk export) with no limit or step-order check; price, role or permission taken from the request body; an upload accepted with no file-type allowlist. CWE-434.
- A07:2025 Authentication Failures. The system can be fooled about who a user is: weak or breached passwords accepted, brute force not stopped, weak multi-factor or recovery, sessions not rotated or invalidated. In a diff: a login or one-time-code endpoint with no rate limit; no new session id after login; JWT verification that accepts "none" or skips the signature; logout that leaves the server session alive; a credential written into the code. CWE-287, CWE-306, CWE-798.
- A08:2025 Software or Data Integrity Failures. Code or data trusted without checking where it came from or whether it was altered: unsigned updates, scripts from a CDN with no integrity hash, deserializing untrusted input. In a diff: pickle.loads, yaml.load with an unsafe loader, Java ObjectInputStream or PHP unserialize on outside data; a script tag with no integrity attribute; a download used with no signature or hash check. CWE-502.
- A09:2025 Security Logging & Alerting Failures. Security events are not logged, are logged badly, or never raise an alert anyone acts on; logs that leak secrets or accept injected lines count too. In a diff: a new authentication or permission-denied path with no log line; tokens, passwords or personal data written to a log; user input logged without neutralizing newlines. CWE-532.
- A10:2025 Mishandling of Exceptional Conditions. Errors and abnormal states are not anticipated or handled safely, ending in a crash, leaked details, or failing open (access granted because a check threw). In a diff: a broad catch that swallows the error around authentication or validation; an error branch that returns "allowed"; no rollback or cleanup on the error path; an error message that carries internal details to the caller. CWE-636, CWE-209, CWE-476.

OWASP API Security Top 10:2023 — risks specific to APIs, final edition (https://owasp.org/API-Security/editions/2023/en/0x11-t10/, CC BY-SA 4.0).
- API1:2023 Broken Object Level Authorization. The endpoint takes an object id from the client and reads or changes that object without checking this caller may touch that specific object. In a diff: a route with an id parameter that queries by id alone, with no owner filter or policy call. CWE-639.
- API2:2023 Broken Authentication. The way the API identifies callers is weak or can be bypassed. In a diff: a JWT decoded without a fixed algorithm or signature check; an API key read from the query string; a new route without the authentication middleware.
- API3:2023 Broken Object Property Level Authorization. The caller may access the object but not every field on it: hidden fields leak out, or the caller sets fields they should not (mass assignment). In a diff: a response that serializes the whole model; an update built from the whole request body (Model(**body), Object.assign(entity, req.body)) with no field allowlist.
- API4:2023 Unrestricted Resource Consumption. Requests can use unbounded CPU, memory, bandwidth, storage or paid third-party calls. In a diff: a page size or limit from input with no maximum; an upload with no size cap; a paid SMS, email or model call per request with no quota or timeout. CWE-770.
- API5:2023 Broken Function Level Authorization. Privileged operations are reachable by ordinary users because the endpoint checks that the caller is logged in, not that they may do this. In a diff: a new admin, DELETE or PUT route with authentication but no role or permission check; a role check only in the frontend.
- API6:2023 Unrestricted Access to Sensitive Business Flows. A legitimate flow (buying, booking, signing up, redeeming) can be automated at scale to hurt the business, with no code bug. In a diff: a new purchase, coupon, referral or signup endpoint with no per-user limit or abuse check; existing throttling removed.
- API7:2023 Server Side Request Forgery. The API fetches a URL the client supplied, letting attackers reach internal services or cloud metadata through the server. In a diff: a webhook, import or preview URL fetched with no scheme and host allowlist, no block on private and link-local addresses (169.254.169.254, localhost), or with redirects followed. CWE-918.
- API8:2023 Security Misconfiguration. The API stack is set up insecurely. In a diff: CORS that reflects any Origin or allows * with credentials; an error handler returning stack traces; debug routes registered in production.
- API9:2023 Improper Inventory Management. Nobody knows which hosts, versions and endpoints are live, so old or debug APIs stay exposed. In a diff: an old version kept alongside the new one without the same protection; test or debug endpoints shipped.
- API10:2023 Unsafe Consumption of APIs. Data from a third-party or upstream API is trusted more than user input. In a diff: an external API response passed into a query, a shell, HTML or eval without validation; redirects followed blindly; no timeout or size limit on the call.

CWE Top 25:2025 — MITRE's ranked list of the most dangerous software weaknesses (https://cwe.mitre.org/top25/archive/2025/2025_cwe_top25.html). The web entries are cited against the categories above. Two notes the lists above do not carry: seven of the 25 entries are memory-safety weaknesses, which matter in C and C++ (and unsafe Rust) — out-of-bounds write and read (CWE-787, CWE-125), use after free (CWE-416), a buffer copy without checking the size of its input (CWE-120), stack-based and heap-based buffer overflow (CWE-121, CWE-122) and NULL pointer dereference (CWE-476); and hard-coded credentials (CWE-798) left the 2025 list but are still a finding, under A07 above and item 3.
